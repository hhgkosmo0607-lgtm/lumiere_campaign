Overview

이 도구가 메우는 두 개의 gap

왜 필요한가

네이버·메타·구글 같은 플랫폼은 각자 자기 채널 성과만 보여주는 대시보드를 이미 갖고 있다. 채널을 가로질러 비교하는 화면은 어느 플랫폼에도 없다 — 자기 채널에서 경쟁 채널로 예산을 옮기라고 알려줄 이유가 없기 때문이다.

지표는 3개로 고정

CTR · 전환율 · ROAS. 새 지표를 늘리지 않는다. 대신 ROI·이익·클릭단가는 마진율이 있을 때만 표에 조건부로 나타난다. 화면을 넓히는 대신 같은 자리에서 관점만 바꾼다.

업로드 = 실제 리포트

사용자가 만든 템플릿이 아니라, 네이버·구글·메타·카카오가 실제로 내보내는 리포트 파일을 컬럼명 그대로 받는다. 노출수/Impr./Impressions처럼 이름이 다 달라도 캐노니컬 필드로 자동 매핑된다.

STEP 01 · parseExcel.js / platforms.js
src/lib/platforms.js · PLATFORM_COLUMNS

업로드 — 리포트를 그대로 받는다

업로드 기능은 사용자가 직접 만든 템플릿이 아니라, 네이버·구글·메타·카카오가 실제로 내보내는 리포트 파일을 그대로 받는다. 플랫폼마다 컬럼명이 다르다 — 노출수 / Impr. / Impressions처럼. PLATFORM_COLUMNS가 각 플랫폼의 네이티브 컬럼명 → 캐노니컬 필드 매핑을 갖고 있다.

네 플랫폼이 공통으로 가진 값만 쓴다 — 소재(ad) 단위는 구글 리포트에 없고, 도달(reach)은 메타만 줘서 둘 다 뺐다.

여기서 원칙이 하나 있다: 플랫폼이 이미 계산해서 주는 CTR·ROAS 같은 비율 컬럼은 받지 않는다. 노출·클릭·비용·전환·매출 같은 원본 카운트만 가져오고, 비율은 항상 aggregate()가 다시 계산한다 (05번에서 왜인지 이어진다).

CSV는 file.text()로 읽는다 — 파일 API의 arrayBuffer()로 읽으면 한글 헤더가 인코딩 깨짐으로 매칭에 실패한다.

STEP 02 · UploadPanel.jsx
useUploadBatch.js · startBatch() / guessProduct()

캠페인 → 제품 매칭, 화면 한 번

파일 하나 = 플랫폼 하나지만, 여러 플랫폼 파일을 한 번에 선택할 수 있다. 실제 리포트 하나엔 보통 여러 제품의 캠페인이 섞여 있으므로(제품별로 미리 쪼개서 받지 않는다), 대기열의 모든 파일을 한 번에 파싱해 그 안의 고유 캠페인명을 전부 모아 캠페인마다 제품을 매칭받는 화면 한 번으로 처리한다 — 파일마다 매칭 화면을 반복하지 않는다.

캠페인명에 이미 확인한 제품명의 단어가 포함돼 있으면 자동으로 추측해 채운다(guessProduct()). 아직 확인된 제품이 하나도 없는 첫 배치라면, 캠페인명에서 플랫폼·캠페인유형 같은 흔한 단어(CAMPAIGN_STOPWORDS)를 걷어내고 남는 부분을 후보로 채운다(stripCampaignStopwords()) — 완전히 빈칸으로 두지 않는다.

회사·채널마다 캠페인 이름 짓는 방식이 달라 100% 맞지는 않으므로 사람이 확인·수정한다.

STEP 03 · useUploadBatch.js

마진율은 제품 단위로, 딱 한 번

제품 매칭이 끝나면 이번 배치에 걸린 고유 제품별로 마진율을 한 번씩만 입력받는다 — 이 역시 파일 수와 무관하게 한 화면이다. 마진율은 캠페인이 아니라 제품의 속성이라, 캠페인 단위로 따로 받으면 같은 제품인데 마진율이 서로 다르게 입력되는 실수가 생긴다.

product가 비어 있으면 그 행은 ‘전체’로 취급돼 필터·표에 제품 관련 UI가 아예 안 보인다(제품이 2개 이상일 때만 노출). margin(마진율)이 있으면 이익·ROI·진짜 손익분기 ROAS를 계산할 수 있다 — 없으면 손익분기선은 ROAS 100%를 쓴다.

STEP 04 · metrics.js
withMetrics(row)

원본 카운트만 채택한다

플랫폼 리포트에는 이미 계산된 CTR·ROAS 컬럼이 같이 들어있는 경우가 많다. 이 프로젝트는 그 값을 쓰지 않는다 — 노출·클릭·비용·전환·매출 같은 원본 카운트만 받아서, 비율은 withMetrics()/aggregate()가 항상 다시 계산한다.

이유는 다음 단계(05)에서 그대로 드러난다 — 비율을 먼저 받아버리면 그 비율들을 나중에 평균 내는 실수를 구조적으로 막을 방법이 없다.

STEP 05 · metrics.js
aggregate(rows)

합계를 먼저 내고, 지표는 나중에

이 프로젝트의 핵심 계산 원칙

채널별 ROAS는 주차별 ROAS 5개의 평균이 아니다. 광고비와 매출을 먼저 합산한 뒤 나눈 값이다. 이 계산은 aggregate() 하나만 쓴다 — 컴포넌트 안에서 직접 지표를 계산하지 않는다.

실제로 있었던 버그다. 주차별 그래프가 그 주의 데이터를 find()로 첫 행 하나만 대표값으로 쓰고 있었다. 첫날 전환이 0이면(광고 시작 직후 흔한 일) ROAS도 0%로 찍혔다 — 그 주 나머지 6일에 전환이 잘 나와서 주 전체로 합치면 실제로는 200%인데도.

src/lib/__tests__/metrics.test.js — 재발 방지 테스트 
// 실제로 있었던 버그: find()로 그 주의 "첫 행 하나"만 대표값으로 쓰던 문제
const rows = deriveWeeks([
  row({ date: '2026-01-01', adSpend: 100, revenue: 0 }),   // 그 주의 첫 행
  row({ date: '2026-01-02', adSpend: 100, revenue: 400 }),
]);
// 주 전체 합산: 광고비 200, 매출 400 → ROAS 200%.
// 첫 행만 봤다면 0%가 나왔을 것이다.

STEP 06 · metrics.js
deriveWeeks(rows)

일 단위 데이터를 주 단위로 버킷팅

week는 저장하지 않는다. deriveWeeks()가 데이터셋 전체에서 가장 이른 날짜를 1주차로 놓고 7일 단위로 버킷팅해서 매번 새로 계산한다. 실제 플랫폼 리포트는 일 단위라 이 변환이 꼭 필요하다.

주차별 그래프에서 광고를 안 돌린 주(채널이 아예 집행을 쉰 주)는 0%가 아니라 값 없음으로 처리한다. 0%로 이어 그리면 “완전히 실패한 주”처럼 보이기 때문이다. 단, 주 일부만 쉰 경우(나흘만 결측)는 남은 사흘로 계산해 끊지 않는다.

STEP 08 · TrendLineChart / CompareBarChart

손익분기선 — ROAS ↔ ROI 전환

손익분기선은 모든 비교 차트에 유지되는 이 화면의 핵심 장치다. ROAS 모드는 기본 100%(광고비=매출)지만 마진율이 있으면 실제로 남는 지점(1 ÷ 마진율)으로, ROI 모드는 항상 0%(이익도 손해도 아닌 지점)로 움직인다 — breakevenValue prop 하나로 통일해서 받는다.

CompareBarChart는 채널 전용이 아니다. {id,name,color,desc,roas,roi} 모양의 배열이면 뭐든 그리는 범용 가로 막대라서, 채널 비교와 제품 비교 양쪽에 재사용한다. ROI는 마이너스가 나올 수 있어 축이 0 아래로도 내려가는데, 값이 축 왼쪽 끝에 가까우면 라벨이 이름과 겹칠 수 있어 손익분기선 안쪽에 라벨을 고정한다.

Verification

검증 방식 — 앱 코드 밖에서 확인한다

npm run verify 스크립트는 화면에 나오는 숫자가 맞는지 세 가지로 확인한다. 핵심은 첫 번째다 — 앱 안에서만 검사하면 계산식이 틀려도 “일관되게 틀린” 상태를 통과시키기 때문에, 오라클(oracle)을 프로젝트 코드와 완전히 분리된 파이썬으로 따로 짰다.

01

독립 오라클 vs 앱 — 10개 업종, 값 6,888개 대조

scripts/verify/oracle.py는 프로젝트 코드를 한 줄도 쓰지 않고 엑셀을 직접 뜯어서 광고비·노출·클릭·전환·매출부터 CTR·ROAS·이익·ROI·손익분기 ROAS까지 다시 계산한다. 화장품·의류·신선식품 등 업종별 샘플 10벌 전체를 대상으로, 전체·채널별·제품별·주차별 값을 1e-9 오차 이내로 대조한다.

02

preview.html ↔ React — 계산식 이중 구현 대조

Firebase 없이 보는 정적 미리보기 preview.html은 React와 완전히 별도로 같은 계산식을 손으로 옮겨 쓴 vanilla JS다. 두 구현이 같은 데이터로 같은 값을 내는지 집계·채널별·주차별 52개 지점과 1,801행짜리 CSV 내보내기 결과까지 문자 그대로 대조한다.

03

집행 공백 24칸 — 0%가 아니라 값 없음인지

가구·여행 샘플은 채널마다 집행 기간이 다르게 설계됐다(구글은 7주차에 시작, 메타는 5~7주차 휴지 등). 광고를 안 돌린 주 24칸이 실제로 0%가 아니라 “값 없음”으로 그려지는지 매번 대조한다.

04

CI가 로컬에서 못 잡는 걸 잡았다

CI를 붙이자마자 실제로 실패했다 — 로컬 npm install은 통과했는데 GitHub Actions에서만 죽었다. vitest@4가 vite ^6/7/8만 지원해서 프로젝트의 vite@5.3.1과 충돌했고, npm이 몰래 얹은 별도 vite@8이 요구하는 esbuild 버전이 기존 버전과 부딪혔다. 락파일과 정확히 일치해야 하는 npm ci만 이걸 엄격하게 걸러냈다.

GitHub Pages 배포도 같은 방식으로 확인했다 — 실제로 하위 경로(/lumiere_campaign/) 구조로 빌드해서 로컬에서 서빙해보고, 파비콘·og 이미지·업로드 예시 파일이 전부 200으로 뜨는 걸 배포 전에 확인했다.
Self-review

부족한 점 및 개선 가능한 점

01

매주 자동 갱신이 없다

지금은 사람이 리포트를 내려받아 직접 올려야 한다. 완전한 해결책(플랫폼 API로 자동 연동)은 로그인·서버·플랫폼 심사가 다 필요한 별도 프로젝트급 작업이라, 그 절반쯤 되는 절충안으로 “CSV 다시 불러오기”를 대신 붙였다. 자동화 자체는 아직 남은 과제다.

02

useUploadBatch가 값 27개를 반환하는 거대 훅

업로드 화면의 상태(대기열·배치·매칭·마진·진행 단계·오류)를 훅 하나가 전부 쥐고 있다. platform부터 resetPanel까지 27개 값을 한 객체로 반환한다 — 화면을 여러 하위 컴포넌트로는 나눴지만, 상태 관리 자체를 더 잘게 쪼갤 여지가 남아있다.

03

preview.html 이중 구현이 매번 동기화 위험을 만든다

React 없이 보는 미리보기를 유지하려고 계산 로직을 손으로 한 번 더 옮겨 썼다. 실제로 exportCsv.js에 마진율 컬럼을 추가했을 때 preview.html 쪽 동기화를 한 번 깜빡했고, npm run verify가 “CSV 내보내기 결과가 다름”으로 잡아냈다. 검증 스크립트가 있어서 버그로 이어지진 않았지만, UI를 바꿀 때마다 사람이 두 곳을 함께 고쳐야 하는 구조적 위험은 남아있다.

04

테스트가 순수 함수 쪽으로 쏠려 있다

metrics.js·exportCsv.js·importSavedCsv.js 같은 계산 로직은 두텁게 테스트돼 있지만, UploadPanel처럼 여러 단계를 오가는 화면 컴포넌트의 통합 테스트는 상대적으로 얕다. 실사용 버그는 결국 브라우저에서 직접 파일을 올려보며 더 많이 찾았다.

Takeaways

마무리

01

합계를 먼저 내고, 지표는 나중에 계산한다

비율의 평균은 비율이 아니다. 주차별 그래프가 그 주의 첫 행 하나만 대표값으로 쓰던 실제 버그(전환 0인 첫날 때문에 ROAS 0% — 실제로는 그 주 합계로 200%)를 겪고 나서, “광고비·매출을 먼저 합산한 뒤 나눈다”는 원칙을 aggregate() 하나로 강제했다.

02

환경이 다르면 신뢰할 수 없다

로컬 npm install은 통과했는데 GitHub Actions의 npm ci에서만 의존성 충돌이 터졌다. 락파일과 정확히 일치해야 하는 엄격한 검사만 걸러낼 수 있는 문제였다 — 내 컴퓨터에서 되는 것과 재현 가능하게 되는 것은 다른 문제라는 걸 CI를 붙이자마자 확인했다.

03

검증은 앱 코드 밖에서 해야 의미가 있다

앱 안에서만 스스로를 검사하면 계산식이 틀려도 일관되게 틀린 상태를 통과시킨다. 프로젝트 코드를 한 줄도 안 쓴 파이썬 오라클로 엑셀을 직접 계산해 10개 업종·6,888개 값을 대조하고 나서야, 컬럼 매핑·주차 나누기·합산 순서가 전부 맞다고 말할 수 있었다.
